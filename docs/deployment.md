# Architecture and deployment

## Website

`site/` contains the first-party landing page, plans and app downloads, PayPal checkout, customer renewal screens, owner console, web player and PWA assets. React routes and server handlers build with Vinext/Vite for Cloudflare Workers.

The checked-in `.openai/hosting.json` declares the `DB` and `BUCKET` bindings without an existing hosting project identity. The maintained `site/build/` sources are required by the build. Keep them when copying or deploying the site.

Production moved to the independent Cloudflare resources below on October 15, 2026. The complete database, migration history, runtime settings and both Android installers were transferred and verified before the domain switched. The former managed host has no runtime service keys; its APIs are retired and safe legacy links redirect to LumaNest. Its private database remains a recovery copy. A GitHub push alone does not deploy this application.

| Main website Worker | `lumanest-tv`; production custom domain `lumanest.tv`; `workers.dev` and preview URLs disabled |
| D1 database | `lumanest-tv-production`, ID `226b9f80-d3c9-471d-b5b4-c4a0c17f9e9d`, binding `DB` |
| R2 downloads bucket | `lumanest-tv-downloads`, binding `BUCKET` |
| Portal PWA overlay | Existing `lumanest-app-support` Worker on `portal.lumanest.tv/*` and `tv.lumanest.tv/*` |
| Stream relay | Existing `lumanest-stream-relay` Worker at `streams.lumanest.tv` |

Run the normal build, then `npm run cloudflare:prepare -- --database-id 226b9f80-d3c9-471d-b5b4-c4a0c17f9e9d` from `site/`. This generates a standalone config beside the built server with real resource bindings and no production route. `npm run cloudflare:deploy -- --dry-run` validates it. Runtime secrets/settings are supplied privately and preserved with `--keep-vars`. The `--production` preparation flag is the explicit step that selects the apex custom domain; it does not change portal or relay routes. See [`site/README.md`](../site/README.md#direct-cloudflare-deployment) for staging, cutover, and rollback commands. The framework's original `dist/server/wrangler.json` remains local/managed build configuration with placeholder bindings; use the separate generated `wrangler-cloudflare.json` for direct hosting.

**Routine production deploy** (from `site/`, after the cutover):

```
npm ci
npm run build
npm run cloudflare:prepare -- --database-id 226b9f80-d3c9-471d-b5b4-c4a0c17f9e9d --production
npx wrangler d1 migrations apply lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json
npm run cloudflare:deploy
```

Always pass `--production` for a live deploy: without it the generated config enables the `workers.dev` address. Apply migrations only when the list shows new files from this checkout. On Windows on ARM, run these with x64 Node 22, because `workerd` has no Windows ARM build.

Existing customer/order records and owner password hashes live in D1. App downloads may live in R2. Neither is included in this repository. Any production data move needs a private backup, restore and verification process. Do not put database exports, payment details or credentials into GitHub.

The approved Android R2 object is `Tuner-1.6.1.apk`, with the size/checksum and custom metadata required by `site/lib/tuner.ts`. Deploy the site change first, then upload the APK from the owner console's Downloads page, which accepts only the file `lib/tuner.ts` names. Android 1.6.0, 1.5.3 and 1.5.2 remain archived in R2. LG's IPK ships with the website's public assets. Native applications continue to run on customers' devices; their full first-party sources remain in `apps/` on GitHub.

## Database transfer and migration bookkeeping

Preserve all imported application tables, the source host's `__appgarden_migrations` journal, and its sequence state. A fresh schema is not a substitute for the existing owner password, recurring-billing credentials, order history, or payment deduplication records. Preserve the existing `PLAYER_COOKIE_KEY` and PayPal merchant configuration; changing the encryption key can make stored billing credentials unreadable.

The imported source journal and Wrangler's migration journal are separate formats. Wrangler defaults to a table named `d1_migrations`, with columns `id INTEGER PRIMARY KEY AUTOINCREMENT`, `name TEXT UNIQUE`, and `applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL`. It recognizes an applied migration by the exact SQL filename relative to `migrations_dir`, including `.sql`. Copying `__appgarden_migrations` alone does not tell Wrangler that the initial schema has already run.

All nine existing SQL files, **0000 through 0008**, were compared with the imported schema and source journal, then adopted into `d1_migrations` without executing their SQL again. The original names and execution timestamps were copied from `__appgarden_migrations`, which remains unchanged as migration evidence. Never mark an unverified migration as applied. The generated direct config points `migrations_dir` to the checkout's `drizzle/` directory. Future changes belong in new migration files; do not edit an already-applied baseline.

After adoption, `wrangler d1 migrations list lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json` from `site/` should report no pending migration for this baseline. Read the stored migration filenames and inspect schema/index definitions to confirm coverage; compare private table counts and copied journal/sequence values without printing customer rows. Do not run `migrations apply` merely to test the transfer. A temporary deployment artifact outside the source checkout may omit `drizzle/`; use a prepared source checkout when managing future migrations.

## Owner access

The live owner console uses LumaNest email/password sign-in at `/manage/login`. Existing owner credentials and recovery information are in the live database. A clean source checkout does not recreate them.

The legacy first-owner bootstrap relies on the managed host's verified identity dispatch. Keep `ADMIN_USER_ID` and `OWNER_SETUP_TOKEN` unset on independent Cloudflare hosting. The standalone entry removes client-supplied `oai-authenticated-*` headers before invoking the application. Privately migrate existing owner credentials instead of enabling a fresh bootstrap or generating a replacement password. Ordinary owner sign-in remains independent of ChatGPT.

## TV provider

The provider maintains customer lines, playlists, channel selection and the hosted customer portal. Its source code is external to this project. The main website calls its API using a private reseller key.

The `lumanest-app-support` Worker adds installable PWA support to the two provider portal domains. Its configuration is in `site/cloudflare/wrangler.jsonc`. Separate Cloudflare redirect rules direct renewals to the first-party website; those rules remain external configuration. The Worker never edits the provider's Content-Security-Policy. If a header or `<meta>` policy would block the injected script, service worker, stylesheet or manifest, it leaves the page unchanged and logs a `pwa_injection_skipped` event naming the blocking directive. The service worker is served at `/sw.js`, whose default maximum scope is already `/`. The portal needs that root scope for its offline fallback across all pages, so the Worker sends no `Service-Worker-Allowed` header.

The `lumanest-stream-relay` Worker supports approved upstream streams through `streams.lumanest.tv`. Its configuration is in `site/cloudflare/stream-relay.wrangler.jsonc`. The main application and relay share a private authentication key, stored as `PLAYER_STREAM_RELAY_KEY` and `STREAM_RELAY_KEY` respectively. Neither key is in Git.

The `STREAM_RELAY_ALLOWED_HOSTS` variable lists the approved provider addresses, as exact public IPv4 addresses and `a.b.c.0/24` networks. Private, loopback, link-local and other reserved ranges are always refused. An invalid list makes the relay answer 503. The main `lumanest-tv` Worker validates relay sources with the same parser, so set the same `STREAM_RELAY_ALLOWED_HOSTS` value on both Workers; when unset, both use the same built-in default. The optional `RELAY_LIMITER` rate limiting binding caps relay requests per Cloudflare location and returns 429 when exceeded. The configuration comments explain the chosen limit.

The checked-in portal/relay configurations omit account IDs; authenticate to the intended LumaNest account and supply `CLOUDFLARE_ACCOUNT_ID` through the deployment environment when maintaining those services. The main preparation script selects the migration account explicitly. Review the generated domain routes and bindings before deploying. Preserve domain registration, email routing and existing provider DNS settings during the website cutover.

## Payments

PayPal order capture, subscription billing and verified webhooks run in server routes. Webhooks are deduplicated by event ID in D1. Records that need review are reconciled from the owner console instead of with manual database edits. Housekeeping runs without cron triggers; see `site/README.md`. The imported baseline must already include `drizzle/0008_chief_barracuda.sql`; do not execute it again on an imported schema. Preserving `lumanest.tv` keeps existing webhook and return URLs. Merchant credentials, webhook registration, product/plan IDs and existing billing agreements remain private runtime state. Automated tests use fixtures and mocked services, without charging a card or spending the reseller wallet.

## TV applications

Android, Tizen and webOS clients are independently built from `apps/`. They use the configured TV service and catalog integrations. Android release signing uses externally supplied key material. Samsung installation requires the appropriate signing identity and TV configuration. Never generate a replacement release key as part of a source migration: it would break update compatibility.

CI validates source and creates development build artifacts. CI does not deploy production, charge customers, install on TVs or obtain private signing keys.

### Pair with your phone

The TV apps set themselves up through `lumanest.tv/pair`, modelled on the OAuth device flow. A TV calls `POST /api/pair/start` and shows the returned QR code and 8-letter code. The customer signs in to the web player on their phone and approves it via `/api/player/pair`. The TV then collects its playlist login once from `POST /api/pair/poll`. Codes expire after 10 minutes. D1 stores only a hash of the TV's device code, and the login stays sealed with `PLAYER_COOKIE_KEY` until the TV collects it, which deletes the row. `/api/pair/*` allows any origin because TV apps are not pages on this site, and it never reads cookies.

The pairing table arrives in migration `0009_device_pairings.sql`. Apply it before deploying the code that uses it: `npx wrangler d1 migrations apply lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json` from a prepared `site/` checkout.

By default a paired TV receives the same M3U URL the web player loads (`<portal>/m3u?u=…&p=…`). If the TV service exposes an Xtream Codes API, set `TV_APP_XTREAM_SERVER` to its base URL (for example `https://tv.lumanest.tv`; a bare host such as `tv.lumanest.tv` means HTTPS). Paired TVs then use Xtream mode, which adds Movies and Series.

### Movies & Series rows (TMDB)

The Tuner apps get their Popular, Featured (trending this week), Top rated and streaming-service rows (Netflix, Disney+, Max, Prime Video, Apple TV+, Hulu, Paramount+, Peacock) from `GET https://lumanest.tv/api/catalog/rows?v=1`; see [`browse.md`](browse.md) for the design and the response shape. The endpoint is public, needs no login and allows any origin. The apps never call TMDB's API themselves, so the key stays on the server; the only TMDB requests a viewer's device makes are the web player's poster images from `image.tmdb.org`.

**TMDB's commercial terms come first.** TMDB's free API key is licensed for non-commercial use only. LumaNest TV is a business, so the owner must obtain TMDB's commercial terms (a commercial API agreement with TMDB) **before** setting `TMDB_API_KEY`. Until then, leave it unset. The endpoint then answers `{"v":1,"source":"none","movie":{},"tv":{},"genres":{}}` with HTTP 200, and the apps fall back to provider categories, with no Popular or Featured rows. Nothing else needs configuring or deploying for that.

After the agreement is in place, run this from `site/`, after the routine deploy's `npm run cloudflare:prepare -- --database-id … --production` step:

```
npx wrangler secret put TMDB_API_KEY --config dist/server/wrangler-cloudflare.json
```

When Wrangler asks, paste either the API Read Access Token (v4, starts with `eyJ`) or the 32-character API key (v3). The endpoint detects which one it is. The secret takes effect at once and survives later deploys. Keep the `--config` flag: without it, Wrangler in `site/` follows the framework's own build config (`dist/server/wrangler.json`), which does not name the `lumanest-tv` Worker. To turn TMDB off again, run `npx wrangler secret delete TMDB_API_KEY --config dist/server/wrangler-cloudflare.json`. The endpoint answers `none` immediately and stops serving any cached TMDB data. TVs that already downloaded the lists keep their own copy for up to 12 hours, so TMDB data can stay on screen for up to 12 hours after the key is removed; allow for that when the agreement ends.

**Attribution is required whenever TMDB data is shown.** Each app's Settings → About must show "This product uses the TMDB API but is not endorsed or certified by TMDB." TMDB's terms also ask for the TMDB logo next to that notice. Follow any further attribution terms in the commercial agreement.

How it runs:

- **Requests per refresh.** One refresh makes 112 TMDB requests for the lists: 22 lists of 5 pages (100 titles each), plus the movie and series genre lists. It then looks up the details of up to 300 movies whose countries of origin are not known yet (see below). At most 5 requests run at a time. Each request times out after 8 seconds, and the whole refresh stops 25 seconds after it starts. This is more than the 50 subrequests per request that the Workers Free plan allows, so the endpoint needs Workers Paid.
- **Countries of origin.** TMDB's list results give a series' countries of origin (`origin`), but not a movie's, and USA only needs them. Each refresh looks up movies with no known origin in their details (`origin_country`, else `production_countries`), Popular first, up to 300 per refresh; origins already found are carried over from the previous copy, so later refreshes only look up new titles. Until a movie has been looked up its `origin` is `[]`, which the apps treat as unknown (the category filter decides).
- **Caching.** The assembled response is kept in each Cloudflare location's Workers Cache API. A copy is fresh for 12 hours, or 1 hour if some lists failed or some movie origins are still to look up; a failed list keeps its previous copy. After that, one request in the location starts a background refresh while every request keeps getting the stale copy. Each active location therefore calls TMDB about twice a day, plus a few hourly refreshes in its first hours while the movie origins fill in. A zone "Purge Everything" in Cloudflare also empties every location's copy; the next request in each location then builds a new one.
- **When TMDB fails.** The stale copy (kept for up to 7 days) is served, and TMDB is not tried again for 5 minutes. A refresh in which no list came back (for example only the genre lists answered), or in which a list's first page failed and there is no previous copy of that list to keep, counts as failed. With no copy at all, the answer is HTTP 503 with `Cache-Control: no-store` and `Retry-After: 300` (the body is the `none` object), so the TVs treat it as a failed request and keep the lists they have. A request with no copy waits at most 15 seconds for a refresh before answering 503; the refresh carries on in the background. The deliberate answer without a key stays HTTP 200. All other answers carry `Cache-Control: public, max-age=3600`.
- **Logging.** Fixed codes only, never the key or TMDB URLs: `lumanest_catalog_key_unrecognized` (once per isolate) when `TMDB_API_KEY` is set but is neither a 32-character v3 key nor a v4 token (for example pasted with `Bearer ` or quotes; the endpoint then answers `none`), `lumanest_catalog_tmdb_unauthorized` when TMDB refuses the key, and `lumanest_catalog_refresh_failed` for any other failed refresh.
- **Changing the services.** The US watch-provider ids for the services are hard-coded, with a comment, in `site/lib/catalog.ts` and checked by `site/tests/catalog.test.ts`. Re-check them against TMDB's US provider list if a service is renamed or split.
- **Posters.** Each title carries TMDB's `poster_path` as `poster` (`"/abc.jpg"`; left out unless it is `/` plus a plain `.jpg`, `.jpeg`, `.png` or `.webp` file name). No backdrops: about 45 bytes per title, about 100 KB on a full answer of 2,200 titles before compression. The key was added within `v=1`; every app ignores keys it does not know. Copies cached before the change carry no posters until the location's next refresh (at most 12 hours). The web player loads these posters straight from TMDB's image CDN (disclosed on `/privacy`); the TV apps don't use them yet.

### Web player Movies & Series

The web player (`/watch`) shows the line's movies and series with Home, Discover, Library and Search ([`browse.md`](browse.md#web-player)).

- **Source.** With `TV_APP_XTREAM_SERVER` set, the Worker reads the line's Xtream lists (`player_api.php`) with the signed-in line's sealed login. The server's host must be approved like a stream host and reached directly: an https host in `PLAYER_ALLOWED_HOSTS`, or an http host in `PLAYER_ALLOWED_HTTP_HOSTS`. A server on a relay host (`STREAM_RELAY_ALLOWED_HOSTS`) can't be used: the stream relay passes only video, audio and playlists, never `player_api.php`'s JSON. An unapproved server is never contacted; `lumanest_vod_server_unapproved` (or `lumanest_vod_server_on_relay`) is logged once per isolate. Without the setting, titles come only from the movie and series entries in the line's M3U playlist (entries named "Show S01E02" become one series per show), and a line with none shows Live TV as before.
- **Checking a line.** `/api/player/diagnostics?profile=vod`, opened by the owner in a browser that is also signed in to the web player, reports whether the server is set and approved, each list's size, item count and time, the poster hosts and the movie file types. It shows counts and origins only. Under `posters`: `none`, `provider`, `tmdb`, `catalogue_host`, `relay_host` and `other_host` count the line's posters by how the player shows them; `catalogue_host_origin` is the host a catalogue build would choose as the line's catalogue image host (or `null`), `catalogue_host_dirs` how many poster directories it uses (501 means more than 500), `catalogue_host_recorded` the host the image route currently accepts for this line (from the last build in this location), and `catalogue_host_probe` the answer to one request for one of its posters, made the way the image route makes it: `status` (0 when there was no answer), `image` (the image type found, or `""` when the answer was not a raster image up to 2 MB, for example a bot-check page) and `ms`. A probe with `status` 403 or 503 and no `image` usually means the host's bot protection refuses the Worker; its posters then show title cards (or TMDB's poster).
- **Caching and limits.** Each line's compact catalogue is kept in the location's Workers Cache API under a keyed hash of the line: served as it is for 30 minutes, then served while one background refresh runs, for up to 12 hours. **Refresh movies & series** in the player's Settings works at most once per 5 minutes per line. A build makes 4 provider requests in turn, reads each list as a stream (at most 48 MB and 50,000 titles per type) and keeps at most 12 MB of compact titles (9 MB of them movies; a longer catalogue is cut and marked truncated). Catalogue image host posters (below) are added after every title is in, only in the room the titles left of the 12 MB (shared between movies and series in proportion to what their posters need), so they never cut a title; a title whose poster doesn't fit keeps its title card. Check `truncated`, `bytes`, `imageHostPosters` and `imageHostSkipped` in `lumanest_vod_build` after a deploy. A build a viewer waits for stops after 40 seconds, a background refresh after 25 (inside the 30 seconds `waitUntil` allows). One build runs per isolate at a time; a request waits up to 15 seconds for it, a second at a time, then gets `503 vod_busy` with `Retry-After`. A build that fails is not tried again for that line for 5 minutes (the last copy is served meanwhile, or the same error with `Retry-After`); **Refresh** still tries. Series and movie details are cached for 6 hours. Logs carry fixed codes and counts only (`lumanest_vod_build`, `lumanest_vod_failed`). On a `workers.dev` address the Cache API does nothing, so there each isolate keeps the catalogue in memory (testing only; production uses `--production`).
- **Posters.** A title matched to a TMDB title of the rows uses TMDB's poster from the rows (`https://image.tmdb.org/t/p/w342/…`, loaded directly in the browser); otherwise the line's own poster; otherwise a title card with its initials. If the TMDB poster fails to load, the line's poster is tried. Line posters on `image.tmdb.org` load directly in the browser. Posters on an approved provider host the Worker reaches directly go through `/api/player/image`, with tokens bound to the line: a sealed directory serves only plain image file names (`.jpg`, `.png`, `.gif`, `.webp`, `.avif`), and a list seals at most 500 directories or addresses. Posters there are kept in the edge cache for 7 days, a missing one for 1 hour and one the provider failed to serve for 10 minutes; a signed-out session gets none. Poster requests are limited per session in each isolate and, with the `PLAYER_LIMITER` Workers Rate Limiting binding that `cloudflare:prepare` adds (namespace `1002`, 1,200 per minute per line), per line across the location. The binding is free; without it the per-isolate limits still apply.
- **Catalogue image host.** Many panels keep their posters on a third-party image host. Each time a line's catalogue is built, the Worker counts the line's posters by host. An `https` host on the default port that serves at least 20% of the line's posters, and at least 50 of them, becomes that line's catalogue image host. A line has one at most: the host with the most posters (a second host's posters show title cards). Never chosen, whatever their share: IP addresses (the relay's hosts are IPv4 addresses), provider hosts in any of `PLAYER_ALLOWED_HOSTS`, `PLAYER_ALLOWED_HTTP_HOSTS` and `STREAM_RELAY_ALLOWED_HOSTS` whatever the poster's scheme, this site's own hosts and anything under them (the request's host, `lumanest.tv`, the customer portal's host and zone, the stream relay's host), `image.tmdb.org`, private, reserved and local names, names ending in a dot, and names that carry an address (`nip.io`, `sslip.io` and similar). Nothing is hard-coded. A name that resolves to a private address some other way (DNS rebinding) is left to Cloudflare's egress, which can't reach private networks; under `wrangler dev` with a real line, such a host could make your machine fetch from its own network, so test with lines you trust. Its posters go through `/api/player/image` exactly like provider posters (line-bound sealed tokens, raster images up to 2 MB, the edge cache, failure memory, the sign-out check and `PLAYER_LIMITER`); the browser never contacts the host. Each poster's link carries a tag (an HMAC of the line and the poster's address), so a sealed directory serves only the posters the catalogue listed, never a name a viewer makes up. Directories get one sealed token each while the list's 500 last; with more (one directory per poster, for example), the busiest keep theirs and the rest share one token for the host's root, each poster carrying its path from there. A poster address with a query needs a token of its own and shows a title card once the 500 are used. The host is kept with the line's catalogue copy (`X-Vod-Image-Host`, 12 hours) and in a small record next to it (8 days, as long as poster links live), in this location's Workers Cache API; each isolate re-reads it every 5 minutes, and at once (at most every 10 seconds) when a poster names another host. Every image request checks the host again against that and against the rules above before the edge cache is used. Redirects are followed only on the same host (at most 4). Requests to the host send a `User-Agent` (`LumaNestPosters/1.0`), no cookie, referrer or login. Each of its posters a browser hasn't cached yet (browsers keep them 7 days) is one Worker request; the edge cache answers repeats. After 20 failed answers in a row for a line, the host is not asked for that line for 10 minutes (per isolate). A poster whose address contains the line's username or password is never asked for and shows a title card. If a later build finds no such host, its posters stop working at once, cached or not. With no copy or record in a location (both expired, or the viewer's catalogue came from another location), its posters show title cards until the catalogue is loaded there again. On `workers.dev` the record lives only in the isolate that built the catalogue. Every other poster (relay hosts, which pass no images, and any other host, which would see the viewer's address) shows a title card; `/api/player/diagnostics?profile=vod` counts them (`relay_host`, `other_host`). The build log `lumanest_vod_build` gives `imageHost` (true or false), `imageHostPosters` (placed) and `imageHostSkipped` (not placed: no room or no free token), never the host.
- **Playing.** Movies and episodes get the same sealed stream tokens as channels, through `/api/player/stream`. MP4, M4V and MOV play in every browser and can be cast; MKV is offered with a warning; AVI, FLV, WMV and similar point to the Tuner app.
- No migration and no new secret are needed. The only new binding is the optional `PLAYER_LIMITER` above, created by `wrangler deploy` from the prepared config. When `TMDB_API_KEY` is set, Popular and Featured rows appear and the player shows the TMDB notice in Settings → About and under Home and Discover.

### Subtitles and trailers

Every Tuner app and the web player get English subtitles for movies and episodes from OpenSubtitles.com, and a Trailer button from TMDB's videos, through three public endpoints on lumanest.tv (design: [`extras.md`](extras.md)). The apps never call OpenSubtitles or TMDB, and no key reaches a device or a browser. Code: `site/lib/extras.ts` (rules), `site/lib/extras-service.ts` (requests, R2, limits) and the routes under `site/app/api/extras/`.

**Read first: OpenSubtitles' terms.** Their [terms of use for integrators](https://opensubtitles.stoplight.io/docs/opensubtitles-api/f43c0749230b3-terms-of-use-for-integrators) decide two things before any secret is set:

- **A paid plan is needed.** One key serving every customer without their own OpenSubtitles account needs a paid plan (Light or above; Light is 20 USD a month for 2,000 downloads a day). A free key allows 5 downloads per IP address a day, and the Worker's address is Cloudflare's, so a free key does not work. One user login used for all customers counts as shared use too. Recommended: a paid plan with only `OPENSUBTITLES_API_KEY` set.
- **No shared copy of subtitle files.** "Keep a copy on your servers and serve it to your other users: No." So lumanest.tv keeps only which files are best for each title (search results), never the files: every viewer who shows a title's subtitles costs one download from the plan, unless their device kept the file (7 days). A shared file cache needs OpenSubtitles' written permission (their Enterprise arrangement); don't build one without it.
- Every app shows "Subtitles provided by OpenSubtitles.com" in the subtitle menu and Settings > About whatever the plan (required on a free key). API access is not a licence to the subtitles, which are user submissions: like the TV content, the rights are the owner's responsibility. If OpenSubtitles asks for a file to be removed, nothing is stored to delete; its search result expires within 30 days, or delete the `extras/v1/subtitles/` objects in R2 at once.

Trailers and the name fallback need `TMDB_API_KEY`, which stays unset until TMDB's commercial terms are in place (see [Movies & Series rows](#movies--series-rows-tmdb)). Without it the trailer endpoint answers `not_configured` and lookups by name answer `unmatched`; subtitles still work for titles with a TMDB id.

**Secrets**, set from `site/` after the routine deploy's `npm run cloudflare:prepare -- --database-id … --production` step (they take effect at once and survive later deploys; keep the `--config` flag):

```
npx wrangler secret put OPENSUBTITLES_API_KEY --config dist/server/wrangler-cloudflare.json
# Optional, only if the plan needs a user login (leave unset on a paid plan):
npx wrangler secret put OPENSUBTITLES_USERNAME --config dist/server/wrangler-cloudflare.json
npx wrangler secret put OPENSUBTITLES_PASSWORD --config dist/server/wrangler-cloudflare.json
```

| Name | Kind | Purpose |
| --- | --- | --- |
| `OPENSUBTITLES_API_KEY` | secret | The consumer API key (opensubtitles.com, API consumers). Unset: lookups answer `not_configured` and the apps show no OpenSubtitles tracks, with no error. |
| `OPENSUBTITLES_USERNAME`, `OPENSUBTITLES_PASSWORD` | secrets, optional | A user login (both or neither). The Worker logs in only to download, at most once a minute, keeps the token sealed with `PLAYER_COOKIE_KEY` in R2 for 23 hours, and never retries credentials OpenSubtitles refused (new secrets are tried). |
| `TMDB_API_KEY` | secret (exists) | Trailers and the name fallback. |
| `OPENSUBTITLES_DAILY_DOWNLOADS` | plain variable, optional (not a secret) | The day's download budget for every client together, a positive whole number. Unset or invalid: **1800** (Light plan: 2,000 a day). After a plan change, set it to about 90% of the plan's daily downloads in the Cloudflare dashboard (Workers & Pages → `lumanest-tv` → Settings → Variables and Secrets → Add, type Text); `keep_vars` keeps it across deploys. |
| `PLAYER_COOKIE_KEY` | secret (exists) | Signs the subtitle file links (HMAC), names clients in the daily count by a keyed hash, marks refused login secrets, and seals the login token. Unset: subtitles answer `not_configured`. Changing it invalidates file links the apps hold (they get new ones with the next lookup) and starts the day's per-client counts afresh. |
| `BUCKET` | R2 (exists) | The `extras/v1/` metadata cache. Without it nothing is cached and everything still works. |
| `DB` | D1 (exists) | The daily download counts (`extras_download_counts`, migration `0010_extras_download_counts.sql`). Without the table, file requests answer 503 and nothing is downloaded. |
| `EXTRAS_LIMITER`, `SUBTITLE_FILE_LIMITER` | Workers Rate Limiting (new, free) | The minute limits below, added by `cloudflare:prepare` (namespaces `1003` and `1004`, created by `wrangler deploy`). These two are the only new bindings: the upstream and miss limits are keys on them. Without them each isolate counts with the same limits. |

**Migration `0010_extras_download_counts.sql`** adds the daily download count table. Apply it **before** deploying the code that uses it, as for `0009` (from a prepared `site/` checkout, after `npm run build` and `npm run cloudflare:prepare -- --database-id 226b9f80-d3c9-471d-b5b4-c4a0c17f9e9d --production`):

```
npx wrangler d1 migrations apply lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json
npm run cloudflare:deploy
```

The list it shows before applying must be exactly `0010_extras_download_counts.sql`. Deployed without it, every subtitle file request answers 503 (`lumanest_subtitles_count_failed`) and nothing is downloaded; lookups and trailers are unaffected. To turn subtitles off, `npx wrangler secret delete OPENSUBTITLES_API_KEY --config dist/server/wrangler-cloudflare.json`: lookups answer `not_configured` at once (devices may cache that answer for 10 minutes, and an earlier `ok` answer for a day, whose file links then answer 503).

**Endpoints.** All are `GET` (and `HEAD`, `OPTIONS`), need no login or cookie, allow any origin and send `X-Content-Type-Options: nosniff`. `v` is optional and means 1; another value is 400 `unsupported_version`. Errors are `{"v":1,"error":{"code","message"}}` with `Cache-Control: no-store`: 400 `bad_request`, 404 `not_found`, 429 `rate_limited` (`Retry-After: 60`, or until midnight UTC over a client's or an IPv6 /48's daily files), 502 `unreadable`, 503 `unavailable` (`Retry-After`). The apps treat any non-200 answer as "nothing" and stay silent.

- `GET /api/extras/subtitles?v=1&type=movie&tmdb=603`, `?v=1&type=episode&tmdb=1399&season=1&episode=3` (the series' TMDB id), or `name=…&year=…` instead of `tmdb` (resolved with TMDB: exact normalized title, exact year, one id; the OpenSubtitles text search is never used). Answer: `{"v":1,"status":"ok|none|unmatched|not_configured|unavailable","tmdb":603,"tracks":[{"id","lang":"en","label","hi","vtt","srt"}],"credit":"Subtitles provided by OpenSubtitles.com"}`, at most 3 tracks, best first (English, not machine translated or forced-only, one file, the right title or episode; not AI translated, then not SDH, then most downloaded). `Cache-Control`: `ok` one day, `none` and `unmatched` 6 hours, `not_configured` 10 minutes, `unavailable` (download quota used up) `no-store`, a stale copy after an upstream failure 5 minutes.
- `GET /api/extras/subtitles/file/<file_id>-<mac>.vtt` or `.srt`: the links a lookup hands out (the MAC is the first 22 characters of the base64url HMAC-SHA256 of `extras-subtitle-v1\n<file_id>` under `PLAYER_COOKIE_KEY`, so only offered files can be downloaded through our quota; anything else is 404). **Every GET is one download from the plan**, so each is counted for the UTC day first (Daily budget below): the Worker asks OpenSubtitles for the file, reads at most 2 MB within 10 seconds from an `https` host under `opensubtitles.com`, converts it to plain-text WebVTT (or SRT), and stores nothing. `HEAD` downloads nothing. Headers: `Cache-Control: private, max-age=604800`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cross-Origin-Resource-Policy: cross-origin`. A file with no usable cue is 502 `unreadable`; with the quota used up, 503 until the reset.
- `GET /api/extras/trailer?v=1&type=movie&tmdb=603` or `type=tv` (or `name` and `year`): `{"v":1,"status":"ok|none|unmatched|not_configured","tmdb":603,"trailer":{"key","name","url","short":"youtu.be/KEY","qr":["0101…"]}}` (`trailer` is `null` unless `ok`): the first official English YouTube trailer (else teaser) from TMDB's `/movie/{id}/videos` or `/tv/{id}/videos`. `qr` is the QR code of `https://youtu.be/<key>` in the format `/api/pair/start` sends.

**How it runs:**

- **Caching (R2, `BUCKET`, prefix `extras/v1/`):** `subtitles/movie/<tmdb>/en.json` and `subtitles/tv/<tmdb>/s<season>/e<episode>/en.json` (the chosen file ids, 30 days, 3 days when there are none), `trailers/movie|tv/<tmdb>.json` (30 days, 7 without a trailer), `resolve/movie|tv/<sha256>.json` (names: 30 days found, 7 not found) and `state/opensubtitles.json` (the quota reset time, the sealed login token, the last login attempt and a keyed hash of refused login secrets). No subtitle file and nothing about a viewer is ever stored there; an object is replaced when it is refreshed after it expires. Each lookup is shared by every customer in every location. An expired object is refreshed while the request waits (8 seconds per upstream request); when that fails, the expired copy is served for up to 90 days with `Cache-Control: public, max-age=300` and refreshed again after 5 minutes. Failures are never cached as "none". To forget everything, delete the `extras/v1/` objects in the R2 dashboard; nothing else depends on them.
- **Download quota:** when OpenSubtitles answers that the quota is used up, the Worker records the reset time (at most 24 hours ahead) and calls OpenSubtitles for no download until then: file requests answer 503 with `Retry-After`, and lookups answer `unavailable`. Each download logs the remaining quota.
- **Daily budget (D1):** each file `GET` is counted before the download, per UTC day: for every client together (row `*`), per client (an IPv4 address, or an IPv6 /64) and, for IPv6, per /48 (a household's /56 or a free tunnel's /48 holds many /64s), stored as a keyed hash (HMAC under `PLAYER_COOKIE_KEY`), never the address. One client gets **60 files a day** and one /48 **240** (then 429 until midnight UTC; an isolate that has seen a client or /48 over its cap refuses it from memory until then, without D1); all clients together get `OPENSUBTITLES_DAILY_DOWNLOADS`, **1800** by default (then 503 until midnight UTC, and the isolate that saw it offers no tracks until then). The day's total counts only requests within those caps, so one client or one /48 can't use it up for everyone; many IPv4 addresses, or a page that hotlinks the file links for many visitors, still can (there is no per-viewer grant). The /48 cap is shared: where an ISP numbers separate customers inside one /48 (mobile carriers, some large ISPs), one heavy user can leave the others there with 429 for files until midnight UTC and for uncached lookups until the minute ends, so a report that subtitles stopped for an IPv6 viewer can be this (`NETWORK_DAILY_DOWNLOADS` in `lib/extras.ts` sets the cap). Customers behind one shared IPv4 address (carrier-grade NAT, iCloud Private Relay) likewise share one client's 60 files a day (`CLIENT_DAILY_DOWNLOADS`). A download OpenSubtitles answered with an error (401, 403, 406, 429, a 5xx twice: no link, so not counted by them) is taken off the counts again, so a wrong key or an outage doesn't use up the day; one that may have counted (a link was given, or `/download` didn't answer) stays. If D1 fails, the file request answers 503 (`Retry-After: 60`) and nothing is downloaded. Rows older than yesterday are deleted by the file route (at most once an hour per isolate) and by the maintenance clean-up. `lumanest_subtitles_budget_low` (past 80%) and `lumanest_subtitles_budget_used_up` are logged once a day per isolate. To see today's total: `npx wrangler d1 execute lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json --command "SELECT count FROM extras_download_counts WHERE client='*' AND day=date('now')"`. To start today's counts over (for example after a problem that used them up without real downloads): `npx wrangler d1 execute lumanest-tv-production --remote --config dist/server/wrangler-cloudflare.json --command "DELETE FROM extras_download_counts WHERE day=date('now')"` (isolates that saw the budget used up offer no tracks, and isolates that saw a client or an IPv6 /48 over its daily cap keep answering it 429 from memory, until they are replaced, for example by a new deploy, or midnight UTC).
- **Limits a minute per client** (`CF-Connecting-IP`: an IPv4 address, or an IPv6 /64 so rotating addresses inside it gains nothing; never stored or logged): 120 lookups (subtitles and trailers together, key `lookup:` on `EXTRAS_LIMITER`), 12 subtitle files (`file:` on `SUBTITLE_FILE_LIMITER`) and 12 lookups that need an upstream request (`miss:` and the client's keyed hash, on `SUBTITLE_FILE_LIMITER`; for IPv6 also 12 for its whole /48, under the /48's keyed hash). Over any of them: 429, except that over the uncached-lookup limit an expired copy under 90 days old is served as a stale copy (`Cache-Control: public, max-age=300`) without a refresh.
- **Upstream limits:** every OpenSubtitles search and TMDB request a cache miss makes first takes a token from `EXTRAS_LIMITER` under the fixed key `upstream:opensubtitles` or `upstream:tmdb` (120 a minute per key in each Cloudflare location, for all clients together). When refused, the request isn't made: the stale copy is served if there is one, else 503, and nothing is cached (`lumanest_extras_upstream_limited`). This keeps made-up titles from turning into OpenSubtitles or TMDB rate limits for real customers, or into R2 writes. The cost: about 10 clients (IPv4 addresses or IPv6 /48s) asking for made-up titles at their full uncached-lookup limit take one service's tokens in a location, and until the minute ends lookups there that need that service and have no stale copy answer 503 (the apps then show no subtitles or no Trailer button); fresh and stale copies are still served. A steady run of `lumanest_extras_upstream_limited` means this is happening. Lookups also accept only seasons 0 to 100 and episodes 1 to 5000.
- **Logging:** fixed codes and numbers only, never keys, tokens, the login, IP addresses or their hashes, titles or URLs: `lumanest_subtitles_search_failed`, `lumanest_subtitles_download` (with `{"remaining":N}`), `lumanest_subtitles_download_failed`, `lumanest_subtitles_quota_exhausted`, `lumanest_subtitles_login_rejected` (once per isolate: check the username and password secrets), `lumanest_trailer_tmdb_failed`, `lumanest_extras_resolve_failed`, `lumanest_extras_upstream_limited`, `lumanest_subtitles_budget_low`, `lumanest_subtitles_budget_used_up`, `lumanest_subtitles_count_failed` (D1 failed or the migration is missing), `lumanest_subtitles_uncount_failed` (a download OpenSubtitles didn't count stayed counted) and `lumanest_subtitles_count_cleanup_failed`. A run of `lumanest_subtitles_download_failed` with no other code usually means a wrong `OPENSUBTITLES_API_KEY` or a lapsed plan.
- **Removing one bad cached entry** (a vandalised TMDB trailer, a wrong subtitle match, or a file OpenSubtitles asked to remove): delete its R2 object, and the next lookup asks upstream again (fix the entry on TMDB first, or it comes back). From `site/` with the prepared config:

  ```
  npx wrangler r2 object delete lumanest-tv-downloads/extras/v1/trailers/movie/603.json --remote --config dist/server/wrangler-cloudflare.json
  ```

  The keys: a movie's trailer `extras/v1/trailers/movie/<tmdb>.json`, a series' `extras/v1/trailers/tv/<tmdb>.json`; a movie's subtitle search `extras/v1/subtitles/movie/<tmdb>/en.json`, an episode's `extras/v1/subtitles/tv/<series tmdb>/s<season>/e<episode>/en.json`; name resolutions `extras/v1/resolve/movie|tv/<sha256>.json` (find one in the R2 dashboard by its date, or delete the whole `extras/v1/resolve/` prefix, which costs one TMDB search per name). `<tmdb>` is the number in the title's TMDB address. Devices may keep an earlier answer for up to a day (`Cache-Control`) and the apps for the rest of their session. Trailers TMDB doesn't mark official are still accepted when there is no official one, so a purge is the remedy for a bad one.
- **After deploying**, check `https://lumanest.tv/api/extras/subtitles?v=1&type=movie&tmdb=603` (`ok` with tracks, or `not_configured` before the key is set) and `https://lumanest.tv/api/extras/trailer?v=1&type=movie&tmdb=603` (`ok`, or `not_configured` without `TMDB_API_KEY`). Opening one of the `vtt` links costs one download.
- **Privacy:** `/privacy` and `tunertv.app/privacy` (`tuner-site/public/privacy.html`) describe the OpenSubtitles lookups (made when a movie or episode starts; the file only when subtitles are shown), the TMDB name lookups, the YouTube trailer (the web player's embedded player in privacy-enhanced mode; on Samsung and LG the same player in lumanest.tv's trailer page, below; the YouTube app or a QR code on the other TVs), the one-minute counting and the daily download count (a keyed hash of the network address for the current UTC day and the next, then removed by routine clean-up). Keep them in line with any change here, and with `docs/store-listings.md`.

### Trailer page

Samsung 1.6.1 and LG 1.2.1 play trailers inside Tuner in `https://lumanest.tv/embed/trailer?v=1&k=<key>`, a page holding YouTube's embedded player that the apps show in a full-screen iframe (design: [`extras.md`](extras.md#trailer-page-get-embedtrailer)). Code: `site/app/embed/trailer/route.ts`, `site/lib/trailer-embed.ts`, `site/public/embed/trailer-frame.js` and `.css`, and their two rules in `site/public/_headers`. It needs no secret, binding or migration, and stores and logs nothing.

- **Deploy the site before installing those apps on a TV.** Until the page is live, every trailer shows "Loading" for 12 seconds and then opens the YouTube app, which makes a TV test misleading.
- **After deploying**, check the headers:

  ```
  curl -sI 'https://lumanest.tv/embed/trailer?v=1&k=L0fw0WzFaBM'
  ```

  It must answer `200` with `Content-Security-Policy: default-src 'none'; script-src 'self' https://www.youtube.com https://s.ytimg.com; frame-src https://www.youtube-nocookie.com https://www.youtube.com; ...`, `Referrer-Policy: strict-origin-when-cross-origin` and `Cache-Control: public, max-age=86400`, and with **no** `X-Frame-Options` header and no `frame-ancestors` in any CSP: the TV apps frame the page from `file://` or an app scheme. Opened directly in a desktop browser, the page stays black (no player); that is expected.
- **No zone-wide security headers.** A Cloudflare zone setting that adds security headers to every response, such as the "Add security headers" managed transform (`X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: same-origin`), would break the TV apps' trailers: `SAMEORIGIN` blocks the `file://` parents, and `same-origin` sends YouTube no Referer (error 153 on engines that ignore the iframe's own `referrerpolicy`). None is on (October 20, 2026: lumanest.tv answers without `X-Frame-Options`). If one is ever wanted, leave `/embed/trailer` out of it.
- Changing `trailer-frame.js` or `trailer-frame.css` means updating its `?v=` in `lib/trailer-embed.ts` (`tests/trailer-embed.test.ts` fails until then). TVs may keep the page and its files for a day.
